# shogi-analyzer

将棋ウォーズの棋譜をローカルで解析する。棋神解析の自前版。課金なし・通信なし。

*A local Shogi Wars kifu analyzer. Runs YaneuraOu + Suisho5 (or Fairy-Stockfish) offline — no fees, no network.*

## 必要なもの

- **Python 3**（標準ライブラリのみ。`pip install` するものは無い）
- **エンジン**。どちらか:
  - **やねうら王 ＋ 水匠5**（推奨。棋神に近い数字が出る）— ソースからビルドする（→[エンジン](#エンジン)、5分）
  - **Fairy-Stockfish** — `brew install fairy-stockfish` 一発。ただし評価値の振れ幅が棋神より小さい

`engines/yaneuraou-nnue` があればそれを、無ければ `fairy-stockfish` を使う（`engine.py` の `default_engine()`）。

動作確認は macOS のみ（`open` と `add.py` の `pbpaste` を使っている）。

```bash
git clone https://github.com/chris9609/shogi-analyzer.git
cd shogi-analyzer
python3 export.py games/20260901_1056.kif   # 同梱の棋譜で試せる
python3 build.py out/20260901_1056.json
open out/20260901_1056.html
```

## 使い方

```bash
# ── ビューア（盤面＋評価値グラフ）をつくる ──
python3 add.py                                    # クリップボードのKIFを取り込む
python3 export.py games/20260901_1056.kif         # 解析して out/*.json
python3 build.py  out/20260901_1056.json          # out/*.html （ブラウザで開ける）
open out/20260901_1056.html
```

```bash
# ── 複数局をまとめて見る ──
python3 stats.py --me christel09                    # out/*.json を横断集計
python3 stats.py --me christel09 --by side          # 先手/後手別
python3 stats.py --me christel09 --by timeControl   # 持ち時間別
```

```bash
# ── CLIで数字だけ見る ──
# 1局まるごと（全手の評価値・損失・最善手・読み筋）
python3 analyze.py games/20260830_0023.kif

# 特定の局面だけ深く読む
python3 analyze.py games/20260830_0023.kif --at 34 --movetime 5000 --pv 12

# 1手あたりの探索時間を伸ばす（既定 1000ms。70手で約1分）
python3 analyze.py games/xxx.kif --movetime 3000

# 候補手を3手まで出す（既定は1手）
python3 analyze.py games/xxx.kif --multipv 3
```

## 棋譜の取り込み

1. 将棋ウォーズの**棋譜再生画面の上部にあるコピーアイコン**を押す（KIF形式がクリップボードに入る）
2. Macで `python3 add.py`

これだけ。ファイル名は棋譜の開始日時から自動で決まり（`games/20260830_0023.kif`）、
そのまま `verify.py` の検算まで走る。画像認識は不要。

iPhoneでコピーしたものをMacで貼るには、ユニバーサルクリップボード（Handoff）が要る。
うまく渡らない場合は、棋譜テキストを直接 `games/なまえ.kif` に保存してもよい。

## 🚨 新しい棋譜は、まず検算を通すこと

```bash
python3 verify.py games/新しい棋譜.kif
python3 verify.py games/新しい棋譜.kif --at 34   # 盤面を出して画面と見比べる
```

**Stockfish系は `position startpos moves ...` に不正な手が混ざると、エラーを出さずに
そこまでで適用を打ち切る。** 変換にバグがあっても、途中までの局面について
「それらしい評価値」が返ってくるので、解析結果を眺めても絶対に気づけない。
`verify.py` はエンジンが報告する手数が期待値と一致するかを見て、これを検出する。

## 構成

| ファイル | 役割 |
|---|---|
| `add.py` | クリップボードのKIFを取り込む（検算まで自動） |
| `kif.py` | KIF → USI 変換。依存ライブラリなし |
| `engine.py` | USIエンジンのドライバ |
| `analyze.py` | 解析本体（CLI出力） |
| `export.py` | 解析してビューア用JSONを吐く |
| `viewer_template.html` | ビューアのテンプレート（`/*__DATA__*/` にJSONが入る） |
| `build.py` | テンプレート＋JSON → 単体HTML。`--bare` でArtifact公開用。タイトルに対局者名が入る |
| `verify.py` | KIF→USI変換の検算 |
| `stats.py` | 解析済みJSONを横断して平均損失などをまとめる |
| `test_kif.py` | KIFパーサーの回帰テスト（エンジン不要、1秒） |
| `games/` `out/` | 棋譜置き場 / 出力 |
| `engines/` | やねうら王のバイナリと評価関数（`suisho5/nn.bin`）。git管理外 |
| `nnue/` | Fairy-Stockfish 用のNNUE評価関数の置き場（152MBなのでgit管理外） |

### ビューアの設計メモ

- 盤は**榧の盤・黄楊の駒**の色から起こしている（`--board` `--koma` 系のトークン）。
  木目は薄い縞のグラデーションを2枚重ねただけで、写真テクスチャは使っていない。
  星（4つの交点の点）も打ってある。駒は五角形のまま、成駒は朱
- 🔑 **盤のマス目は `grid-template-rows:repeat(9,1fr)` が要る**。
  これが無いと段の高さが中身に引きずられ、**駒のある段だけ背が高くなる**（46px vs 26px）。
  盤全体は `aspect-ratio:1` で正方形に見えるので、目視では気づきにくい
- 配色は先手＝藍 `#1D6FB8` / 後手＝朱 `#C0402F` / 強調＝金 `#B8892B`。
  色覚特性を含む検証を通してある（ライト・ダーク両方でPASS）
- **悪手は色だけでなく将棋の記号 `?!` `?` `??` でも示している**（色に頼らない）
- 🔑 **盤のマス目は起動時に一度だけ作り、以降は中身だけ書き換えている。**
  毎手 `innerHTML` で作り直すと81マス＋駒が丸ごと捨てられて作り直されるので、
  「次の一手」を押すたびに盤がちらつく（押し続けると特に目立つ）。
  筋・段の目盛りは反転したときだけ、持ち駒は中身が変わったときだけ書き換える
- 🔑 **棋譜欄の追従に `scrollIntoView` を使わない。** `block:"nearest"` でも
  ページ全体がスクロールすることがあり、手を送るたびに画面が動く。
  棋譜欄の `scrollTop` を自分で計算して、その中だけで位置を合わせている
- **評価値グラフは将棋ウォーズの形に寄せている**（線形の縦軸 ±2000・500刻み、10手ごとの縦線、
  1手ごとに点を打った赤い1本線、手数の目盛りは0の線に沿って中に）。見慣れた形のほうが読み違えない。
  以前はtanhで中央を引き伸ばしていたが、ウォーズと見比べたときに形が違って混乱するのでやめた。
  悪手の `?!` `??` はグラフには打たない（点と重なって読めない）。棋譜欄と棋神の行にある
- **候補手は3手まで並べ、それぞれの読み筋を下に添えている**。1位を濃く、2位以下を
  退かせて、目が最初に最善手へ行くようにした
- 🔑 **候補手の評価値も先手視点に揃えてある**（エンジンは手番側視点で返す）。
  同じ画面に向きの違う数字が並ぶと、どちらが得なのか読み違える
- ヘッダに「どのエンジン・評価モード・何msで測ったか」を出している。
  評価値はものさしが変われば意味が変わるので、数字だけ切り出されても分かるように
- 読み筋は盤面から駒を引いて日本語表記に直している（`7g7f` ではなく `▲7六歩(77)`）。
  そのためにUSIの指し手を盤面に適用する処理を持っている（成り・駒取り・打ちに対応）
- **「棋神」ボタン（`K` キー）で、その局面の最善手を盤に矢印で出す**（打つ手は着地点に駒名）。
  盤の下に「棋神の一手 / 実際に指した手（損失・記号）」を並べ、一致なら ✓。
  矢印は盤の上に重ねた SVG 1枚を `renderBoard()` の中で属性だけ書き換えているので、
  反転（⇅）にも追従し、手を送っても作り直さない。`moves[].n` は「指した後」の手数なので、
  局面 `ply` から指された手は `n === ply + 1`（`lastMoveSquare` の `n === ply` とは逆向き）

## パーサーのテスト

```bash
python3 test_kif.py     # エンジン不要、1秒で終わる
```

将棋ウォーズのKIFは移動先を必ず完全な座標で書くので、`同`・`不成`・`成銀` は
実棋譜に一度も出てこない。他のソース（ぴよ将棋・Kifu for Windows など）の
KIFを食わせると出るので、テストで固定してある。

- `同` は**実棋譜を機械的に「同」表記へ書き換えて、元とUSIが一致するか**で見ている。
  手で期待値を書くより取り違えにくい（20260830_0023 で14手、20260901_1056 で13手が対象）
- `不成`・成駒名（`成銀` `成桂` `成香` `と` `馬` `龍` `竜`）・`打`・`右左上` の修飾は
  `_to_usi` の単体テスト
- `変化：N手` 以降は分岐の読み筋なので、本譜に混ぜない（混ぜると手数が巻き戻った
  指し手が続きとして入り、黙って別の将棋になる）

移動元の括弧があるときは駒名を見ていない（成るかどうかの判定にしか使わない）ので、
**駒名が間違っていてもパーサーは気づかない**。そこは `verify.py` がエンジン側で拾う。

## エンジン

USIプロトコルで喋れるものなら何でもよいが、起動オプションの語彙がエンジンごとに違うので、
`engine.py` は `id name` で見分けて出し分けている。対応は次の2つ。

### やねうら王 ＋ 水匠5（推奨）

将棋専用のエンジンと評価関数。Fairy-Stockfish から替えたら、同じ対局で
**棋神のグラフにかなり近い数字**になった（2026/09/11 の対局、先手視点）:

| 手数 | Fairy-Stockfish | やねうら王＋水匠5 | 棋神（画面を目視） |
|---|---|---|---|
| 40 | −435 | −773 | −1500 |
| 55 | +276 | +733 | +1300 |
| 57 | −230 | −781 | −1500 |
| 70 | −711 | −1481 | −2000 |
| 80 | −1016 | −2164 | −2000 |

Fairy の数字は探索を15秒に伸ばしても変わらなかったので、時間ではなくエンジンの差。
形（どこで落ちるか）は Fairy でも合っていた。違うのは振れ幅。

セットアップ（macOS / Apple Silicon）:

```bash
mkdir -p engines && cd engines
git clone --depth 1 https://github.com/yaneurao/YaneuraOu
cd YaneuraOu/source
make -j normal COMPILER=clang++ TARGET_CPU=APPLEM1 YANEURAOU_EDITION=YANEURAOU_ENGINE_NNUE
mv YaneuraOu-by-gcc ../../yaneuraou-nnue          # 🔑 名前を "yaneuraou" にしない（下記）
cd ../..
brew install sevenzip
curl -sL -o Suisho5.7z https://github.com/yaneurao/YaneuraOu/releases/download/suisho5/Suisho5.7z
7zz x -osuisho5 Suisho5.7z && rm Suisho5.7z         # → engines/suisho5/nn.bin（64MB）
```

`engines/` はまるごと git 管理外。評価関数は `engines/<名前>/nn.bin` を自動で探す
（`find_eval_dir()`）。水匠5は [やねうら王のリリース](https://github.com/yaneurao/YaneuraOu/releases/tag/suisho5) にある。

- 🔑 **バイナリを `engines/yaneuraou` という名前にしてはいけない。** macOS のファイルシステムは
  大文字小文字を区別しないので、クローンした `YaneuraOu/` ディレクトリと同じ名前になり、
  `mv` がディレクトリの中へ移動してしまう（「permission denied」で気づく）
- 🔑 **`FV_SCALE` は評価値の物差しそのもの。** 既定16だが水匠5は24が推奨で、`engine.py` が設定している。
  ここが違うと数字の大きさが全部変わる
- 対局用の仕組み（定跡 `BookFile`、`NetworkDelay`、`MinimumThinkingTime`）は `engine.py` で全部切っている。
  定跡を引くと探索せずに手を返してくるので評価値が出ない
- 積めたかどうかは `isready` のときの `info string loading eval file : <path>` で確認している。
  読めなければ `Error! : failed to read nn.bin` を出して落ちる（Fairy と違って黙って続けない）
- **不正な手が混ざるとプロセスごと終了する**（`Illegal move`）。`verify.py` はこれも拾って、
  どの手が疑わしいかを出す。Fairy の「黙って途中で止まる」とは逆の流儀
- `--classical` は Fairy 専用。やねうら王のNNUE版は評価関数なしでは動かない

### Fairy-Stockfish

`fairy-stockfish`（Homebrew: `brew install fairy-stockfish`）。チェスの Stockfish を
多ゲーム対応にしたもので、`UCI_Variant=shogi` で将棋になる。Apple Siliconでそのまま動く。
手軽だが、将棋専用エンジンと比べると評価値の振れ幅が小さい（上の表）。

#### NNUE評価関数

`nnue/` に `*.nnue` を置いておくと自動で積む（`engine.py` の `find_nnue()`）。
将棋用のネットは Fairy-Stockfish 公式の一覧から取る:

```
https://fairy-stockfish.github.io/nnue/   →  shogi-878ca61334a7.nnue（152MB）
```

152MBあるのでリポジトリには入れていない（`.gitignore` 済み）。置かなければ
評価関数なしの classical 評価で動く。明示的に切るなら `--classical`。

#### 🚨 積めたかどうかは、エンジン自身に名乗らせて確かめること

**評価関数ファイルとエンジンのNNUEアーキテクチャが合っていないと、エラーではなく
無言で classical に落ちる。** ファイルが置いてあることは「積めた」の証拠にならない。

`engine.py` はエンジンが吐く `info string` を拾って `eval_mode` を `NNUE` /
`classical` に確定させ、`describe()` で出す。`analyze.py` と `export.py` は
これを必ず頭に印字するので、**出力に `NNUE` と出ていなければ積めていない**。

```
エンジン: Fairy-Stockfish 14.0.1 XQ / NNUE (shogi-878ca61334a7.nnue)   movetime 1000ms
```

🔑 **この `info string` は `usi` でも `isready` でもなく、最初の `go` のときに出る。**
起動直後に評価モードを知るために、`engine.py` は `go movetime 1` の空打ちを1回入れている。

### エンジンを替えるときの注意

`d` コマンドの出力（盤面と SFEN の行）はエンジンごとに形が違う。`Engine.board()` に
1か所にまとめてあるので、別のエンジンを足すならそこを直す。`export.py` と `verify.py` は
それを通して**手数の検算**をしているので、ここが合わないと解析が始まらない（始まらないのは正しい）。

🚨 **エンジンや評価関数を替えたら、`out/*.json` は全部解析し直すこと。** 評価値の物差しが
変わるので、混ぜたまま `stats.py` で平均を取ると意味のない数字になる。

## 実装上の注意（ハマった点）

- 🔑 **パイプに `go` と `quit` をまとめて流すと探索が即打ち切られる。**
  `bestmove` を読むまでプロセスを開いたままにすること（`engine.py` がやっている）
- 🔑 **USI の `score cp` は「手番側から見た」値。**
  そのままグラフにすると先手と後手が交互に勝っているようなギザギザになる。
  後手番の局面では符号を反転して、全部「先手視点」に揃えている
- 🔑 **詰み(`score mate N`)を大きな点数に変換したまま引き算すると、損失が9万点になって壊れる。**
  損失計算の前に評価値を ±`--clamp`(既定2000) に丸めている。
  「もう決着している局面での上下」は損失として数えない、という考え方
- KIF は移動元が括弧で入っている（`６八銀(79)`）ので、盤面を再現しなくても変換できる。
  `成` が末尾なら成る動作、先頭なら成駒の駒名（`成銀`）、`不成` は成らない、で判別している
- 🔑 **KIFの `同　歩(76)` は「同」と「歩」の間が全角スペース。**
  行を `(\d+)\s+(\S+)` で切ると `\s` が全角スペースにも当たるので、指し手が「同」で
  切れて移動元を落とし、`移動元が読めない` で落ちる。指し手は行末まで取って、
  うしろの消費時間 `( 0:03/00:00:23)` を落としてから空白を除くこと
- 🔑 **MultiPV>1 のとき、「最後にスコアが載っていた info 行」を採ってはいけない。**
  `multipv 1/2/3` の行が反復ごとに流れてくるので、最後の行＝3番目の候補手＝
  いちばん悪い手の評価値を、局面の評価値として拾ってしまう（実測で1番 -7 / 3番 -38）。
  さらに**順位ごとに最後の行を採るのも駄目**で、最終反復が途中で打ち切られると
  順位2と3が別々の反復から来て、**同じ手が2回並ぶ**（直す前は局面の約2割で発生）。
  `engine.py` は depth ごとに束ねて、順位が出そろった反復のうち一番深いものを丸ごと使う
- 🔑 **平均損失は「どのものさしで測ったか」で意味が変わる。**
  エンジン・評価モード・探索時間が違う解析を同じ折れ線に並べると、腕前が変わって
  いないのに上下したように見える。`export.py` はJSONに `engineInfo` を書き残し、
  `stats.py` はその組み合わせごとに束を分けて、混ざっていれば警告を出す

## 検算

`games/20260830_0023.kif` は**70手目に後手(christel09)が投了**した将棋。
解析結果が終盤にかけて先手優勢（+3000〜詰み）に振れていれば符号の向きが正しい。
逆に後手優勢と出たら、どこかで視点の反転が抜けている。

NNUEに差し替えたあともこれで答え合わせができる。実際、69手目は `▲詰16`、
平均損失は 先手31 / 後手83（`--movetime 1000 --multipv 3`）で、向きも大きさも妥当だった。

### 🚨 境界付近の判定は、同じ棋譜でも走らせるたびに変わる

時間制限の探索なので、**同じ棋譜・同じ設定で2回解析すると評価値が中央値で17点ずれ、
`?!`/`?`/`??` の判定が69手中4手で入れ替わった**（`--movetime 1500`）。
MultiPV を 1 と 3 で変えたときの差（3手）と同じ大きさで、つまり
**MultiPVのせいではなく、探索のばらつきそのもの**。

- 「300点級の悪手を拾う」用途には支障ない
- **「悪手が2個から3個に増えた」を上達・下達の根拠にしてはいけない**。
  数え方の精度がそこまで無い。`--movetime` を伸ばせばばらつきは減る
